# Secrets, personal data and security (mandatory)

Full threat model and controls: `docs/SECURITY.md`.

## The OpenRouter key

- The key is read only from `.streamlit/secrets.toml` or the `OPENROUTER_API_KEY` environment variable, through one config function (`get_api_key()`). `.streamlit/secrets.toml` and `.env` are gitignored; only `.streamlit/secrets.toml.example` with a placeholder is committed.
- Never hardcode, log, print, display, or put the owner's key in exceptions, `st.session_state`, tests, issues, PRs or commit messages. Never open the real secrets file. (If the "bring your own key" option in `docs/DEPLOYMENT.md` is built, a visitor's own key may live in the session only, under the same never-log, never-show rules.)
- **No anonymous visitor may spend the owner's key.** A public deployment must use one of the options in `docs/DEPLOYMENT.md`. Until then the app runs locally only.
- **The USDA FoodData Central API key** (`USDA_FDC_API_KEY`, optional, T9.9) follows the same rules: read only through `get_food_api_key()` from the same two places, never logged, shown, put in an exception, `st.session_state`, a test, an issue, a PR or a commit; sent only in the `X-Api-Key` header to `config.FOOD_API_URL`, never in a URL, and redirects are refused. Only the food name the model passes goes to that API, after `api_query()`'s check and, in a coach's chat, the check against the coach's clients' full display names, as whole words (`src/tools/food_api.py`); never a profile value. The check is a heuristic: a plain word from the chat can pass with the name (known limit in `docs/SECURITY.md`), so every in-app privacy note says food names may go to USDA's API when the key is set. Tests never reach it (`tests/conftest.py` replaces its opener and fails a test that sends a request).

## The chat socket and its token (T11.4a, T11.4b, D24)

- **The token secret** (`[chat] token_secret` in `.streamlit/secrets.toml`, or `FITKOMPASS_CHAT_TOKEN_SECRET`) follows the OpenRouter key's rules: read only by `config.chat_token_secret()` (at least 32 characters; the example's placeholder counts as none), never hardcoded, logged, printed, shown, put in an exception, `st.session_state`, a test, an issue, a PR or a commit (`tests/test_realtime_tokens.py` scans for its names outside `src/config/environment.py` and for the reader's callers). A token is a bearer secret too: never logged, shown, put in a URL or an error.
- **The acting user comes only from a token that verifies.** The token (`src/realtime/tokens.py`) holds only the keyed user ID, the thread and the expiry (`config.CHAT_TOKEN_TTL_SECONDS`, 15 minutes), signed with HMAC-SHA256. It is minted only by the Messages page (`views/messages.py` through `src/realtime/page.py`, T11.4b), on each run of the thread's fragment, for the acting user it works out from `st.user` or, in demo mode, the picker's closed list, as everywhere else; never from a form, a URL, a frame or a model argument. The page hands it to the browser component in its `data` only: never in a URL, `st.query_params`, `st.session_state` or a log, and the component keeps it in memory (no `localStorage`, `sessionStorage`, cookie or `setStateValue`; `tests/test_messages_component.py` scans for these). The server never takes a user or a thread from anything else the browser sends, and never adds a frame field that names one.
- **The server** (`src/realtime/`, a FastAPI app mounted with `st.App` on Streamlit's own server by `serve.py`, so `streamlit run serve.py` serves the pages and the socket from one process and one port, D24 as revised in T11.4b) serves at `config.CHAT_MOUNT_PATH` + `config.CHAT_SOCKET_PATH` on the host Streamlit binds (`server.address = "localhost"`), with Streamlit's access log off; it refuses a handshake whose `Origin` is not one of the local hosts (`config.CHAT_LOCAL_HOSTS`) on the port Streamlit serves or one of `config.CHAT_PUBLIC_ORIGINS` (empty until a public deployment adds its own https origin, `docs/DEPLOYMENT.md`), or whose URL has a query string, takes the token as the first frame only, never in the URL, keeps the thread out of the socket's path, verifies each renewal like the first token, closes a socket whose token expired unrenewed, and reads and writes messages only through `src/store/messages.py`, checking the recipient through the store's read before every push. A message the store refuses gives the sender a fixed error, never the reason.
- **Its logs and tracing:** the socket runs no model and never calls LangChain, so nothing it does is traced; never add a model call or a tracer to it (a model call on a message needs the gymer's consent, T11.5). Once the server has started, `serve.py`'s lifespan hook (`server.quiet_library_logs`) sends uvicorn's, asyncio's and the web libraries' loggers (`server.LIBRARY_LOGGERS`) through `observability.capture_library_logs()` at WARNING (after uvicorn set its own loggers up, which would undo it at import), for Streamlit's own socket too, so they write no handshake line (it holds the client's address), request line or traceback; never turn them up, give them a handler of their own or let them propagate. The socket handler catches every exception and logs only `llm.error_diagnostic(exc)`, so uvicorn never logs a traceback (which could quote a message). FastAPI's own OpenTelemetry (spans, metrics, logs with an error's message and stack trace) stays off (`telemetry` in `create_app()`); never turn it on. No log line holds a message's text, a token, a user, a thread or an address (`tests/test_realtime_server.py` runs `streamlit run` on a wrapper like `serve.py` in a child process with a canary over every line it writes). `streamlit run app.py` alone serves no socket, and the Messages page says real-time messages are off (`server.mounted()`).

## The LangSmith key and tracing (T9.8)

- The LangSmith key is read only by `config.get_langsmith_api_key()`, from `.streamlit/secrets.toml` or `LANGSMITH_API_KEY`, under the same rules as the OpenRouter key: never hardcoded, logged, printed, shown, put in a run, a test, an issue, a PR or a commit.
- Tracing is off unless the app's flag `FITKOMPASS_TRACING` and the key are both set. Never turn tracing on another way (LangSmith's `LANGSMITH_TRACING`, `tracing_context`, `langsmith.configure`, a tracer passed in `callbacks`, `@traceable`): only `tracing.configure_tracing()` installs the client, and only its client masks. Never use `.with_retry()` or a LangGraph `RetryPolicy`: a retry's event carries the error's message and the reply past the mask (`tests/test_tracing.py` scans for these, and for an import of `langsmith` outside `src/tracing.py` and `src/experiments.py`).
- **Never traced:** the drafts from a photo or a voice note (T11.10) run inside `tracing.untraced()`, which turns tracing off for the calls made in its block only (LangSmith's `tracing_context(enabled=False)`, inside `src/tracing.py`), so the file, its description or transcript and the cards reach no trace, masked or not, the demo's unmasked ones included (`tests/test_tracing.py`, with the demo gate open). Never run a part of that workflow outside it, and never use `untraced()` to turn tracing on.
- **The two unmasked paths.** First (T9.33, owner's choice, 2026-11-12): `scripts/run_evaluation.py --langsmith` records the evaluation as a LangSmith experiment through `src/experiments.py`, whose client masks only a run's error (`tracing.mask_error_only()`) and whose tracer reaches a turn only as a `tracing.RunTrace` passed to `chat.run_turn()`. It holds only the evaluation's own data (the owner's questions and good answers, a made-up profile, CC BY chunks, prompts and answers). Only the evaluation script imports `src/experiments.py` (scanned in `tests/test_tracing.py`); never pass a `RunTrace` from the app, never install the experiments' client as LangSmith's global client, never run an experiment on a user's data, and never make an experiment's traces public (they hold the text of chunks found and not cited, without their attribution, and the owner's prompts; compliance run 1 of T9.33).
- **Second, unmasked traces of the app's own runs exist only in demo mode (T9.35, owner's decision, 2026-11-13).** `tracing.build_demo_client()` is the only client for the app's own runs whose anonymizer can let a payload through (an error keeps only its class name, `tracing.mask_error_only()`), and only while `tracing.demo_gate_open()` is true: `configure_tracing()` opened the gate (tracing on, `FITKOMPASS_TRACING_DEMO_UNMASKED` on, `config.demo_mode()` true) and demo mode is still on, with any error reading as closed. Never add another way to send an unmasked payload, never make the gate depend on anything a user, a form, a URL or the model can set, and never set the flag for a public deployment or with `[auth]` (demo mode is then off anyway). The demo project's name is `config.LANGSMITH_DEMO_PROJECT`; the page warns, in both languages, while the gate is open. Never make a demo trace public (no LangSmith share link, no public export): it holds chunk text without its source's credit and the owner's prompts (copyright rules 6 and 7, as for T9.33's experiments). Show it on the owner's screen or through a workspace invitation; in a published video, show the question, the tool calls and the answer, and chunk text only together with its source's credit. Change the flag only with the app stopped: a run that starts without a rerun of the page (no such run exists today) would keep its thread's old project name. Tests: `tests/test_tracing.py`, `tests/test_app_my_data.py`.
- Every other run (all but these two paths) is masked by `tracing.mask()` (an allowlist by key). A new state field, tool result or metadata key must not hold data under a kept key's name (`code`, `status`, `kind`, `name`, `type`, a token or counter key, `turn_id`, LangGraph's node fields, and `prompt_answer`, `prompt_query`, `prompt_review`, kept only as 12 lowercase hex characters, T10.4); a new kind of run with personal data gets a case in `tests/test_tracing.py`.
- Every new graph run carries a `turn_id` in its config's metadata (`tracing.run_metadata()`), the same one its log lines carry.

## Logs

- Log only through the app's loggers (`logging.getLogger(__name__)` in `src/`; `views/`, `scripts/` and `app.py` write no log lines, which `tests/test_observability.py` scans for): `src/observability.py` writes JSON lines to stderr and keeps only the fields on its allowlist. Add a field to `ALLOWED_FIELDS` only if it is an id, a count, a code, a status or a duration, and update the list in `docs/SECURITY.md`.
- **Never log** the question, a rewrite, the answer, chunk text, a profile value, a tool argument or result, the key, an error's message or traceback (`exc_info`), or a name the model made up (a tool name). Log `LLMError.diagnostic` or `llm.error_diagnostic(exc)` instead of an error. Use a fixed event name, never an f-string or `%s` argument with data.
- The event is one of `observability.EVENTS` (`turn`, `guard_rejected`, ...; add a new one there); anything else is written as `unnamed_event`. Field values are plain (text, numbers, booleans, `None`, flat lists): pass `llm.error_diagnostic(exc)`, never `exc`. Never turn up the level of the `openai`, `httpx`, `httpcore`, `httpx2`, `httpcore2`, `langsmith` or `authlib` loggers or their child loggers (below WARNING they could log URLs, response headers, errors, LangSmith's run IDs and error text, the sign-in's PKCE `code_verifier`, and in other versions the prompt, the profile or the key); `configure_logging()` keeps them at WARNING (the OpenAI SDK 3.x sends through `httpx2` and `httpcore2`, T1.12). Never set uvicorn (Streamlit's server) to DEBUG: it would log a short excerpt (start and end) of every websocket message, a short one in full; at INFO it already writes each browser connection's address to stderr under `streamlit run app.py` (under `streamlit run serve.py` the lifespan hook routes its loggers through the JSON formatter at WARNING, so that line is dropped), and library warnings reach stderr in their own format (`docs/SECURITY.md`).
- Every new log call carries the `turn_id` when it runs inside a turn. A new ending of a turn needs a test in `tests/test_observability.py` that its lines hold none of the canary values.

## Model clients

- Build chat and embedding clients only with `build_chat_model()` and `build_embeddings()` in `src/llm.py`; they check the model allowlist and cap `max_tokens` when the client is built.
- **Never pass `model`, `max_tokens`, `max_completion_tokens`, `base_url` or `reasoning_effort` at call time** (`.bind(...)`, `invoke(..., max_tokens=...)`, `model_kwargs`, `extra_body`): call-time arguments override the client's settings and would get around the allowlist and the cap. For another model or budget, build a new client.
- **Never change a built client** either: no assigning its fields (`chat.max_tokens = ...`, `chat.model_name = ...`), no `model_copy(update=...)`, no `configurable_fields(...)` or `configurable_alternatives(...)`. These bypass the checks in the same way.
- **The one pass-through** is OpenRouter's routing object (`provider`: only the named providers, no fallback), set by `build_chat_model(providers=...)` when the client is built, so a consent text that names the model's provider stays true (T11.5: the draft model is pinned to `config.DRAFT_PROVIDERS`; T11.10: the photo and voice models to `config.MEDIA_PROVIDERS`, built only by `media.build_model()`); it holds nothing else, and `tests/test_client_rules.py` allows `extra_body` only there.
- `tests/test_client_rules.py` scans `src/`, `views/`, `app.py` and `scripts/` for the three rules above (T9.2); it cannot see a method reached through `getattr` or kept in a variable, so review still checks those.

## Personal data

- **Guests:** the profile (weight, height, age, sex, activity, goal) lives in `st.session_state` only for the session. Nothing a guest enters is written to disk.
- **Signed-in users** (T9.6; the sign-in is T9.5's): the acting user's ID is worked out on every run from `st.user` (an HMAC of the issuer and `sub`) or, in demo mode, the picker's closed list of synthetic users; never from a form, a URL or a model argument, and the Google name, email and picture are never stored, logged or shown. The account (keyed ID, role, display name), the profile history, weights, food and workout logs, targets, preferences, relationships and scopes, reviews, the questions to the coach and the answers under approved reviews (T9.25), invitations, code attempts, the audit rows, from T9.34 the lists of foods a coach suggests to a client and the mark of a food logged from one, from T11.7 the meal plans a coach sets for a client (each food with its grams and their nutrients), from T11.8 a coach's recipes (the coach's own content: a name, the steps in their own words and USDA foods with grams and their nutrients, every version kept), the mark on a meal item a gymer logged from one (`meal_items.from_recipe`, the recipe's ID) and the gymers' ratings of recipes (1 to 5 stars, every rating kept, the newest counting), from T11.3 the messages between a coach and a client (the thread, the sender, the time and the text), from T11.5 the gymer's Art. 9 consents to send their data to a model (`ai_consents`: the purpose, the relationship for (b) and (e), the version of the text agreed to, when given and when withdrawn) and which of the gymer's messages the drafting workflow has finished with (`message_drafts`, the message's ID only), and, from T9.29, each user's notification read mark (the reader's own ID and a time; the notifications themselves are worked out from the other rows and never stored) are stored in the local SQLite store (`src/store/`, the file in gitignored `data/store/`) and, from T9.16, the weekly review threads in the checkpointer's file (D12; metrics, not chat messages); nowhere else on disk. Chats are never stored.
- Stored or not, personal data is never logged (`tests/test_observability.py` runs the store with canary values), never sent anywhere except the LLM call that needs it (and, for the chat's food tool, the food name checked by `api_query()` to USDA's FoodData Central API, T9.9; known limit in `docs/SECURITY.md`), never shown to anyone but the user and, within the scopes the user shares, their coach (the relationship itself, its dates and scope history, the other side's ID, and the audit rows of the coach's reads and review decisions are seen by both sides, in their exports too; from T9.12 each side also sees the other's display name on screen (the coach in the client list, the gymer on the sharing page, and from T9.29 both in their notifications), though not in the export; a user's notification read mark is seen only by them and is only in their own export; from T9.25 a question to the coach and its answer are seen by the gymer and, by the rule of the review it belongs to, that review's coach, and are never sent to a model; from T11.3 a thread of messages is read by its two sides only, also after the relationship ended, and holds both sides' messages in both exports; from T11.8 a coach's recipes are read by the clients connected with them now, and a gymer's ratings reach the coach only as a recipe's average and count over the clients who share nutrition with the coach now, shown from `config.RATING_MIN_RATERS` of them and never who rated (with few clients the coach may still work out a rating, a known limit in `docs/SECURITY.md`); a gymer's ratings are in their export only, the recipes in the coach's), and never put in the vector store. An error raised by the store names the field, never the value.
- **The store** (`src/store/`): only the standard library's `sqlite3`, embedded; every query is a constant string with `?` parameters, never SQL built with f-strings, `%`, `.format()`, `+` or `.join()` (`tests/test_store_sql_scan.py`). The sharing rule is written once, as the `open_shares` view in `schema.py`; every read of another user's data goes through `access.authorised_read()` (from T9.12, the other side's display name excepted: read by `users.display_name_of()`, which checks the relationship instead and is not audited, owner's choice, 2026-11-03; and from T9.30 a coach's question notifications: `questions.list_question_events()` checks `access.authorise_read()` and the review's scopes in `open_shares` like `list_questions()`, is in the refused-cases matrix and holds no text, but audits the coach's own list only when its caller passes `audited=True`, which only the Notifications page does, on each run (a read of one named client is always audited); the sidebar's count and the toasts read it unaudited, the one exception to auditing every allowed read, the middle way, owner's choice, 2026-11-08), and a query that filters by sharing reads the view: a coach, of a gymer, an active relationship and the scope shared (body, nutrition, training; preferences never), else the same `NotFound`; a coach's read, every review decision and every answer to a question (T9.25, `review_answered`) write an audit row with no values; a question or an answer is written only through `questions.py`, by the rule of the review it belongs to. No coach relationship starts for a gymer who has not saved a profile (T11.17): `invitations.accept_invitation()` refuses the code (`no_profile`) before the try is counted and again inside the transaction that starts the relationship, before the code is checked, so the code stays unused and the coach is told nothing; as every profile entry passed the age check, the coach's writes below reach only a gymer who declared an adult age (self-declared, never verified). `users.start_relationship()`, the demo seed's step with no code, does not check it; a gymer who later deletes every profile entry keeps the relationship, as does a relationship made before T11.17, and the pages hide the coach's target, plan and the week again (T11.7). There are three writes into another user's records. The first is a coach's target for a client (T9.17, `records.add_client_target()`): it runs `access.authorise_read()` for the record's scope inside its write transaction, with the insert and the audit row `target_set`, and is in `tests/test_store_access.py`'s group of a coach's writes, refused wherever a read is; a coach-set target is never deleted by the gymer alone (only `my_data.delete_user_data()` removes it). The second is a coach's list of suggested foods for a client (T9.34, `suggestions.add_client_suggestions()`): the same check inside its write transaction, with the inserts and the audit row `suggestions_set`, in the same group of `tests/test_store_access.py`; the gymer reads the list of the coach they are connected with now and logs from it (`meal_items.from_suggestion`, set only after the store checked the item is on that list), never changes or deletes it; a list goes with either side's data; neither the list nor the share logged from it is sent to a model. The third is a coach's meal plan for a client (T11.7, `meal_plans.add_client_meal_plan()`): one template day of meal slots from the food log's fixed list (no free text), each with USDA foods, grams and their nutrients; the same check inside its write transaction, with the inserts and the audit row `meal_plan_set`, in the same group of `tests/test_store_access.py`; a plan with foods whose day's energy is below `config.CALORIE_FLOOR_KCAL` is refused in the store (`BelowCalorieFloor`), and an empty plan removes it; the gymer only reads the plan of the coach they are connected with now (nothing is logged from it), never changes or deletes it; a plan goes with either side's data and is in the gymer's export (the coach's export keeps only the audit rows); it is not sent to a model in T11.7 (T11.9 sends its foods only with the gymer's consent (d), `docs/PRD.md`). The audited actions are `access.Action` (`read`, `review_approved`, `review_edited`, `review_rejected`, `review_answered`, `target_set`, `suggestions_set`, `meal_plan_set`), the same list as the `audit_log.action` CHECK; a new one is added by a migration that builds `audit_log` again (`schema._V4`, `schema._V5`, `schema._V6`, `schema._V9`). The messages between a coach and a client (T11.3) are the third exception to reading through `access.authorised_read()`: `messages.py` checks the relationship itself, like `users.display_name_of()`: a thread (a `coach_clients` row) is read only by its two sides, also after the relationship ended, and written only by them while it is active, with the end read as a value (`ended_at`), never as a sharing filter; every other case gets the same `NotFound` and writes nothing. A thread read is not audited (owner's choice, 2026-11-19): both readers are parties to the conversation, and an audit row for every message pushed to an open page would flood the log; so are the message notifications (one per thread, the newest message from the other side, never its text). A message's text is never logged or traced, and reaches a model only with the gymer's consent for that purpose (`docs/PRD.md`, "Privacy changes in the Capstone"): from T11.5 the gymer's own messages (never the coach's) go to the draft model only on the gymer's press, with consent (a) to the current text checked in the store right before each call (`ai_consents.is_given()`), after the guard, and the run's state stays in the session's memory. The Art. 9 consents (`src/store/ai_consents.py`, T11.5) are one open row per user and purpose, and per relationship for (b) and (e), which count only while that relationship is active (its end read as a value) and are deleted with it; only the gymer gives or withdraws their own, and a consent is withdrawn by setting `withdrawn_at` once, the one change its trigger allows (as `consents.revoked_at` is set), so giving it again adds a row. The drafted mark (`message_drafts`, T11.5) is written only for the gymer's own message, by `drafts.mark_finished()` (a no-op when it exists) or with the step's entries by `drafts.save_step()` in one transaction that first checks the message has no mark; it refers to the message and goes with it, and no logged entry refers to a message. The coach's recipe library (T11.8) is the fourth exception, with the owner's choices of 2026-11-19: a recipe is the coach's own content, written, edited (a new version, the recipe keeping its ID) and deleted only by its coach (`recipes.save_recipe()`, `recipes.delete_recipe()`), and read by the coach and the clients connected with them now, sharing or not (`recipes.list_recipes()`), the relationship read as a value (`ended_at`), as `messages.py` does, and not audited, as it holds none of a gymer's data. A gymer logs a recipe only through `records.add_recipe_items()`, which checks in its write transaction that the recipe is their current coach's (`recipes.recipe_for_client()`) before it writes one marked meal item per food, scaled by the gymer's factor in `config.RECIPE_PORTION_RANGE`; the mark is the recipe's ID with no foreign key (`recipes` is keyed with AUTOINCREMENT, so an ID is never given again), kept by an edit only while the food stays the same, and left as it is when the coach deletes the recipe or their data. A gymer rates a recipe (`ratings.rate_recipe()`) only while its coach is their current coach and after they logged it; every other case is the same `NotFound`. The coach's read of their recipes' ratings (`ratings.rating_summaries()`) counts only the newest rating of each client who shares nutrition with the coach now, read from `open_shares` (so the count cannot tell the coach that a client who does not share logged the dish), returns nothing for a recipe below `config.RATING_MIN_RATERS`, not even the count, and is not audited, as it holds no single person's value: a recorded exception to auditing every allowed coach read. A recipe's steps are shown as Markdown with every image and link as plain text (`src/recipes.steps_markdown()`), so a coach's text loads nothing from another server and links nowhere. Neither a recipe nor a rating is sent to a model in T11.8 (T11.9 scales a coach's recipes in code). Deleting a recipe deletes its versions, foods and every client's rating of it; a coach's delete of their data deletes their recipes with them, and a gymer's deletes their ratings. The store file runs in write-ahead log mode (WAL) so the chat socket (D24) reads and writes it on connections of its own next to the pages' (a commit never waits for a reader); `connect()` refuses a file it cannot switch to WAL (`StoreError`), every connection sets `journal_size_limit = 0`, and `delete_user_data()` and `records.delete_record()` checkpoint the log after their commit (`db.checkpoint()`, which never raises), so deleted rows' earlier copies leave the `-wal` file then, or, when another connection's transaction that outlasts the checkpoint's short wait (`config.STORE_CHECKPOINT_WAIT_SECONDS`, a quarter of a second; a long read, or any store call, as each takes the write lock) keeps the checkpoint from finishing (logged as `store_checkpoint` with its status only), once a later checkpoint completes (the next delete's, SQLite's automatic one after about 1000 pages, or the last connection's close). A new public function in `src/store/` is classified in `tests/test_store_access.py` (a read goes through the refused-cases matrix; the display-name read of T9.12 through its own group). The authorisation lives in the store, never only in the UI or the prompt. Records are never updated in place (a new row instead); the one exception to keeping every row is the notification read marks (T9.29, owner's choice, 2026-11-06): `notifications.mark_all_read()` adds the reader's new mark and deletes their earlier ones in the same transaction, so the table is no log of when a user read their notifications; foreign keys are on and never cascade, so `my_data.delete_user_data()` names every table, and a new table that refers to users must be added to it and to `export_user_data()`.
- Use synthetic data only in demos and tests; the store file is not encrypted (`docs/SECURITY.md`).
- The PDF summary is built in memory and downloaded by the user; the server keeps no copy.
- **A photo or a voice note (T11.10, D29):** only with the gymer's consent (c) (`ai_consents`, purpose `media`, checked in the store right before each of the two model calls), and only on the gymer's press. The file is read from the widget into memory, checked (`media.clean_photo()`: JPEG or PNG by content, at most `config.PHOTO_MAX_BYTES` and `config.PHOTO_MAX_PIXELS`; `media.clean_voice()`: a PCM WAV from `st.audio_input` only, never an uploaded audio file, at most `config.VOICE_MAX_SECONDS`) and re-encoded from its pixels or samples alone, so no metadata or tag leaves the app; a file refused here reaches no model. The file, its description or transcript and the cards are never written to disk, a log line or a trace: the run's state lives in the session's `InMemorySaver` and is forgotten when the run ends, the file stays in the run's context (never in a checkpoint), and the widgets get new keys after a press so it is not sent twice (Streamlit keeps the upload in the session's memory until the browser removes it or the session ends). Streamlit's server reads an upload with Starlette, which would write a part over 1 MB to a temporary file: `media.keep_uploads_in_memory()` raises that threshold (`config.UPLOAD_SPOOL_MAX_BYTES`) before the widgets are drawn, and `server.maxUploadSize` in `.streamlit/config.toml` (`config.UPLOAD_MAX_MB`, 6 MB) refuses a bigger body while it streams; never lower the one or raise the other without the other (`tests/test_media.py`). Only the approved entries are stored, as hand-logged ones are (`drafts.save_entries()`), referring to no file. The first call sends the owner's fixed instruction and the file only (no profile, message or name); the second sends the guarded text as data with T11.5's draft instruction.

## Chroma: embedded only

chromadb has known, unfixed vulnerabilities in its HTTP server (accepted risk in `docs/SECURITY.md`; four advisories ignored in CI with reasons). They do not apply as long as:
- Chroma runs only embedded in the app's process (`chromadb.PersistentClient` / `langchain_chroma.Chroma` with a local `persist_directory`). Never start a Chroma server (`chroma run`, Docker image), never use `HttpClient` or `AsyncHttpClient`, never expose Chroma on a port.
- Embeddings come from our OpenRouter client. Never use Chroma's built-in embedding functions or pass `trust_remote_code`.
- When a fixed chromadb release exists (Dependabot will propose it), upgrade and remove the matching `--ignore-vuln` lines from `.github/workflows/ci.yml`. Never add an ignore without a documented reason in `docs/SECURITY.md`.

## Guards

- Every path that reaches the LLM or the embedding API goes through the input guard first; rejected input makes no API call. A gymer's message reaches the draft model only after `guard.check_text()` (the input guard and the domain guardrails) passed it; a refused one is marked finished and never sent (T11.5).
- **The one exception (T11.10, owner's decision, 2026-11-19, in T11.10's criteria):** the first model call of a photo or a voice note sends the file before any guard, as the guard reads text: the whole file reaches OpenRouter and OpenAI, people, documents or labels in it included (a known limit in `docs/SECURITY.md`). It carries only the owner's fixed instruction (O19) and the cleaned file, and only after the size and type checks and consent (c); the text it returns then passes `guard.check_text()` (the input guard and the domain guardrails) before the extraction, and a refused text makes no draft and no further call. Consent (c)'s text and the page's warning say so in both languages and ask the gymer to keep people, documents and labels out of the photo and to record only their own voice. Never add another model call that no guard checks first.
- User input and retrieved text are data, not instructions: delimited, never concatenated into the system prompt. Tool arguments are validated (types and ranges) before a tool runs.
- The domain guardrails in `docs/PRD.md` are enforced in code where possible (e.g. the calorie floor, the age limit), not only in the prompt.
- LLM output is rendered as Markdown without `unsafe_allow_html`.

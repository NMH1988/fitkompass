### T11.11 (P1) The coach's own video link and a click counter (S) · status: todo · issue NMH1988/fitkompass#18
**Serves:** Capstone (`docs/BRIEF_CAPSTONE.md`): E1b in part; Sprint 3 (`docs/BRIEF_SPRINT3.md`): none; Sprint 2 (`docs/BRIEF.md`): none; beyond the brief (owner's request, 2026-11-19) for the counter.
**Depends on:** T11.4a, T11.8
**Acceptance criteria** (proposed by Claude and approved by the owner, 2026-11-19, with the choices in the Notes)
- [ ] A coach adds a video link to their recipe; a link that is not https or not on the allowed hosts in config (`youtube.com`, `www.youtube.com`, `youtu.be`, `vimeo.com`) is refused - parametrised tests.
- [ ] The recipe's video button goes through the chat server's redirect, which adds one to that recipe's count, stored as a row with the recipe only (no user ID and no time, so the table is no timed log of one client's clicks), and redirects only to the link stored for that recipe (an unknown recipe or any other target gets a 404), does not count a request whose `Sec-Fetch-Site` header is `cross-site` (another site's web page in the same browser) or that has no such header (an older browser, where another site's page could not be told apart) but still redirects it to the stored link, so the button works in every browser and no page can raise a count, and counts only `same-site`, `same-origin` and `none`, as the app's own page is on another port, so its clicks arrive as `same-site`; the link's host is built from the same config value as the page's address (`localhost`, `.streamlit/config.toml`), never another name for the same machine such as `127.0.0.1`, which a browser treats as another site; and the redirect catches every exception like T11.4a's socket handler (a fixed answer, diagnostic fields only, no traceback) - `TestClient` tests, an open-redirect attempt, a `cross-site` request and one with no header redirected but not counted and a `same-site` request counted among them (one parametrised test over the four header values, a missing one and a malformed one), a test that the link's host equals the page's address, T11.4a's canary test on a real `uvicorn.Server` extended to a redirect that raises, and the owner's live check: a click on the button in a real browser raises the count.
- [ ] The video button names where it opens (YouTube or Vimeo, from the stored link's host), in English and German - AppTest.
- [ ] The coach sees each recipe's click count, and the gymer's button says, in English and German, that the coach sees how many times it was clicked - AppTest.
- [ ] The counts table is named in `my_data.delete_user_data()` (deleted with its recipe) and in the coach's export, and in `.claude/rules/security-privacy.md`'s list of stored data; `docs/SECURITY.md` records two known limits: with one client a count shows that client clicked, and the redirect takes no token, so a program on the same computer that can reach the local server can raise a count, and anyone who guesses a recipe's ID can be sent to its stored link (accepted by the owner while the app runs locally only, 2026-11-19, with the fixes of code review round 7 of T11.1; another site's web pages, and a browser that sends no such header, are redirected but not counted; a page served from another `localhost` port arrives as `same-site` and is counted, inside this limit; a public deployment needs a token or a signed link) - store tests (the coach's export holds no click time), review.
- [ ] `docs/PRD.md` AC-52 holds; `code-reviewer`, `/security-review` (a redirect), and their reports on the PR.
**Notes:** P1; the first ticket cut if time runs short; the click counter is beyond the brief (owner's request, kept on 2026-11-19). **The owner's choices (2026-11-19):** a request not counted is still redirected to the stored link; the allowed hosts are YouTube's and Vimeo's; the link and the counter both stay.

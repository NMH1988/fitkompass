### T11.9 Dish suggestions for a meal of the plan, with code checks, two pauses and a YouTube search button (L) · status: todo · issue NMH1988/fitkompass#16
**Serves:** Capstone (`docs/BRIEF_CAPSTONE.md`): Case 2 steps 1-3 (the agent's second workflow), E2a, E2b; Sprint 3 (`docs/BRIEF_SPRINT3.md`): none; Sprint 2 (`docs/BRIEF.md`): none.
**Depends on:** T11.7, T11.8, O20
**Acceptance criteria** (proposed by Claude and approved by the owner, 2026-11-19, with the choices in the Notes)
- [ ] For a meal slot of the coach's plan, the graph (D27) offers at most 3 dishes (config): the coach's recipes scaled to the plan's grams first and, when fewer fit, well-known dishes the model names in the app's language from part of the slot's ingredients (each at most the plan's grams) plus the basics list - graph tests with a scripted fake model.
- [ ] Model-backed suggestions are limited per gymer per day (a number from config, e.g. 10; suggestions from the coach's recipes alone, with no model call, do not count), and the tokens and cost show as in the chat; the daily count is stored (owner's choice, 2026-11-19), named in `.claude/rules/security-privacy.md`'s list of stored data and in D25, in the gymer's export and deleted with their data - tests of the limit, AppTest.
- [ ] The daily limit's day is the `Europe/Berlin` day (D21); a call that fails or yields no valid dish counts or not as the Structure phase sets, stated on the page; only the current day's count is kept (the earlier days' rows are deleted in the same transaction: a second recorded exception to keeping every row, after T9.29's read marks, so the rule's "one exception" sentence is reworded), the coach never sees it, and it is in the gymer's export only - store tests, review.
- [ ] The plan reaches a model only with the gymer's consent (d) (`docs/PRD.md`, the Capstone's consents), given or withdrawn in one click, stored with the version of its text and checked again right before each model call through T11.5's consent functions; without it only the coach's recipes are offered, scaled by code, and no model is called - a graph test with a fake model that is never called.
- [ ] Every dish shown passes the code checks (ingredients in the plan or the basics list in config, grams within the plan, macros from the USDA data, the day's planned total with the dish in place not below the daily calorie floor); a dish that fails is dropped, never shown - parametrised tests, a model that proposes a food outside the plan or a made-up amount among them, and a valid single-meal dish well under the daily floor that is shown.
- [ ] The graph pauses for the gymer's pick and again for the approval to log; nothing is logged without the second - graph tests (`interrupt()` and resume), AppTest.
- [ ] A dish name the model writes passes the domain guardrails' checks (medical conditions, T9.16's diagnosis wordings) or the dish is dropped - parametrised tests.
- [ ] A dish the model named shows a "Find recipes on YouTube" button whose link is the configured search URL with the dish's name and the app language's word for recipe ("recipe" in English, "Rezept" in German), quoted with `quote_plus`, and whose label or help text says it opens YouTube (Google) in a new tab and searches for the dish's name; no URL from the model reaches the page; no embed, thumbnail or logo - tests of the link builder and of the page.
- [ ] A dish the model named is labelled as AI-generated in English and German (a coach's own recipe is not); the values carry the USDA credit; the masked trace and the log lines hold no plan values or dish text - AppTest, canary tests.
- [ ] `docs/PRD.md` AC-49 holds; `code-reviewer`, `/security-review` (model output to links and to the store), `compliance-reviewer`, and their reports on the PR.

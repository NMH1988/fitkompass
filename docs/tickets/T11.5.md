### T11.5 Draft log entries from a gymer's messages, approved by the gymer, with Art. 9 consent (L) · status: todo · issue NMH1988/fitkompass#12
**Serves:** Capstone (`docs/BRIEF_CAPSTONE.md`): Case 2 steps 1-3 (the agent's first workflow: multi-step reasoning and tools with a human in the loop), E2a, E2b, E3; Sprint 3 (`docs/BRIEF_SPRINT3.md`): none; Sprint 2 (`docs/BRIEF.md`): none.
**Depends on:** T11.3, T11.4b, O19
**Acceptance criteria** (proposed by Claude and approved by the owner, 2026-11-19, with the choices in the Notes)
- [ ] The consents table of D25 holds one Art. 9 consent per purpose (`docs/PRD.md`, the Capstone's consents (a)-(d)), apart from the sharing scopes; this ticket offers consent (a), drafts from the gymer's own messages, whose text names the purpose, what is sent, OpenRouter and the model provider; the gymer gives or withdraws it in one click; it is stored with its times and the version of the text agreed to (a changed text asks again before the next flow), in the gymer's export and deleted with their data; it is checked again right before each model call; without it no message of theirs reaches a model, and another purpose's consent does not count. The table's functions hold these rules for every purpose (a)-(d), and keep, for consent (b), the relationship it belongs to (one open consent per purpose, and per relationship for (b); a (b) of an ended relationship counts as missing; the export lists every row), so T11.6, T11.9 and T11.10 only add their texts - store tests per purpose (a text version kept, a changed text asking again, a withdrawn or missing consent refused, a (b) of an ended relationship refused) and a graph test with a fake model that is never called.
- [ ] With the consent, and only when the gymer presses the button to draft entries from their messages (never on its own, on a page load or a timer), the graph (D26) takes the gymer's own new messages only (never the coach's), runs the input guard and the domain guardrails on each, extracts food, weight and workout entries (exercises from the fixed list, sets, reps and kg checked in code) with structured output, matches foods to the USDA data and computes their values in code, and pauses with a draft card; a rejected message makes no draft and no model call - graph tests with a scripted fake model, parametrised with benign and rejected messages.
- [ ] Nothing is logged until the gymer approves a card; edit and reject work; an approved entry is stored like a hand-logged one (values from the USDA data, never from the model's text) - tests, and AppTest of the card.
- [ ] A message is drafted once. The cards of one message are decided together in one step (each card approved, edited or rejected, then saved at once), so a message is never half decided, and leaving before that step logs nothing, which makes drafting it again safe. The store keeps one row per message the graph has finished with (its cards decided in that step, no card found in it, or rejected by the guard), unique per message, so a later session never sends that message to a model again. One store function writes the step's approved entries and the message's row in one transaction (`BEGIN IMMEDIATE`, so two steps wait for each other) and first checks, inside it, that the message has no row yet: if it has (the same message drafted in two tabs, say), nothing is written and the card says the message was already handled; a failed write leaves neither. The row refers to the message and is deleted with it (so with either side's data), and no logged entry refers to a message, so neither side's delete is blocked and the gymer's food log stays intact when the coach deletes their data; it is in the gymer's export, and `docs/PRD.md`'s "Newly stored" list names it - store tests (a row's write that fails leaves no entry; a second step for the same message writes no entry; each side's delete succeeds and leaves the other side's log intact), and a graph test that an approved, a rejected, a card-less and a guard-rejected message are not drafted again in a new session, and that a message with two cards, one approved and the session ended before the step was saved, logs nothing and is drafted once more, never logging an entry twice.
- [ ] `.claude/rules/security-privacy.md` ("Personal data", "The store") names the consents table and the drafted mark among the stored data, and its "Guards" section says a message reaches a model only after the guard - review.
- [ ] The card says the draft was made by an AI model, in English and German - AppTest.
- [ ] No log line or trace holds a message, a draft's values or the prompt's data (masked tracing, canary tests) - `tests/test_observability.py`, `tests/test_tracing.py`.
- [ ] `docs/PRD.md` AC-46 holds; `code-reviewer`, `/security-review` (messages reach a model), `compliance-reviewer` (health data to a model with a new consent), and their reports on the PR.

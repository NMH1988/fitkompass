### T11.24 (P2) A client's name the coach types is read as the chat's reference (M) · status: todo · issue NMH1988/fitkompass#60
**Serves:** Capstone (`docs/BRIEF_CAPSTONE.md`): Case 2 step 4 (the coach names a client in the chat as they would to a person), E1b (the interaction: no question back about which reference a name is), E3 (a client's name the coach types reaches no model when the matcher reads it; the limits are in the docs criterion); Sprint 3 (`docs/BRIEF_SPRINT3.md`): none; Sprint 2 (`docs/BRIEF.md`): none.
**Depends on:** T9.17 (done), T11.6a (done, NMH1988/fitkompass#47; order only, as both change the coach's chat in `views/chat.py` and the client tools)
**Acceptance criteria** (proposed by Claude on 2026-11-27 and approved by the owner on 2026-11-28, with (a) chosen for which words are read; made exact after code review round 1 of NMH1988/fitkompass#61 and approved by the owner the same day, with the same aim)
- [ ] **A name becomes the chat's reference before the question reaches any model.** In a coach's chat, each client's name the coach types in a question is replaced by that client's reference in this chat (`client-N` of `ClientRefs`, `src/tools/coach_clients.py`), given then if the client has none yet, so a question such as "Summarize what Sam and I wrote this week" can be answered without `list_my_clients` first. The mapping runs after the input guard and the domain guardrails passed the question and before the plan node (`src/agent/graph.py`), so the chat model, the query translation model and the search queries sent to the embedding API all get the mapped text, never the name. The clients read are every client the coach has had, active or ended, grouped by the client's user ID (a client with two relationships counts once); an ended client's reference gets the tools' same "not found" - unit tests of the matcher; a graph test with a fake model whose first call receives the reference and calls `get_client_thread` and `get_client_week` with it, both found; the same graph test asserts that the translation model's input and the search queries hold the reference and not the name.
- [ ] **The matcher's cases.** A name matches as whole words, all its words in a row, without case (as `preferences.names_in()`), after the text and the names are both normalised (NFKC, so full-width and other compatibility forms read as plain letters, and accents dropped, so "Zoe" reads as "Zoë"); with the English possessive ("Sam's" becomes "client-1's"; "Jonas'" and "Jonas's" for a name ending in s) and the German genitive ("Sams Nachrichten"), the latter only when "Sams" is not itself a client's name; when names overlap ("Sam" and "Sam Lee") the longest is read first; all names are replaced in one pass over the question, so a reference already put in is never read again (a client named "Client", "Coach" or "client-2" never turns "my client Sam" into "my client-3 client-1"); a name inside a code span, a link or a URL is replaced too; a word that only contains a name ("Samuel", "maximum" for "Max") is never replaced. Besides the full display name, a single word of it (at least two letters, typed with a capital first letter) is read as the client when no other client the coach has had, active or ended, has that word in their name; a name or word two different clients share (by user ID) is left as typed, and the model then asks which client is meant, as today. A second client with "Sam" in their name who joins in the middle of a chat makes a later "Sam" stay as typed, while earlier questions keep their reference - parametrised unit tests for each case, including gymers' display names that are everyday or chat words ("Client", "Coach", "Protein", "Will", "client-2"), benign English questions that must come out unchanged, and German questions whose capitalised nouns must stay unchanged unless they are a client's name or a word of it ("Wie viel Protein isst Koch?" changes only when a client is called Koch).
- [ ] **The coach sees what was read.** Under the question, the page writes in code, never left to the model, one line per matched word naming whom it was read as ("Sam: read as your client Demo gymer Sam"), in English and German, with the display name shown as plain text (escaped, links broken, as `tables.one_line()`); the lines are kept with the chat's message, so they stay after a rerun and follow a switch of language; a question with no match shows no line - AppTest in both languages, with a match, two matches and none, a rerun and a language switch.
- [ ] **What is kept and shown.** The question kept in the chat's memory and sent again in later turns (`src/agent/memory.py`) holds the reference, never the name; the page and the PDF summary show the question as the coach typed it (the owner's choice, 2026-11-28), and the answer with names, as today (`with_client_names()`, `views/export.py`); "New chat" forgets the references and the mapped questions together - AppTest (the shown question, a second turn whose model input holds no name), a PDF test of the typed question.
- [ ] **The checks stay as they are.** The input guard and the domain guardrails check the question first, and the mapping reads the guard's cleaned text (`decision.text`), never the raw input; a question they refuse reaches no model; when the mapped text is longer than the guard's length limit (a short name replaced by a longer reference), the turn is refused with the guard's own too-long message and reaches no model; a preference that names a client, by name or by reference, is still refused (`preferences.check_preference()`); the food tool's check against the coach's clients' full display names (`src/tools/food_api.py`) stays - the existing tests pass unchanged, plus a test of a question at the length limit whose mapping makes it too long.
- [ ] **No name reaches a model.** `test_no_name_or_user_id_reaches_any_message_of_the_coach_s_chat` gets a case where the coach types a canary display name in the question: no message of the turn, the system prompt, the question, a tool call or a tool result, the translation model's input and the search queries hold it; the same for a second turn of the same chat; no log line or trace holds the name or the mapping (`tests/test_observability.py`, `tests/test_tracing.py`).
- [ ] **The owner's live check.** With a real model, in demo mode, in English and in German: the coach asks "Summarize what Sam and I wrote this week" (and the German counterpart) in a new chat; the page's line says whom "Sam" was read as, and the answer reads the thread without asking which client is meant; if the model still calls `list_my_clients` first or asks, the tool descriptions get a line (choice 3 in the Notes) - recorded in `docs/TESTING.md`.
- [ ] **Docs.** `docs/SECURITY.md` (the client tools' row: its limit "the model's own text may still name a client if the coach typed the name in the question") and `docs/TESTING.md` (known limit 9) say what is left: a name or word two clients share; a name typed in a form the matcher does not read (a nickname, a misspelling); a German noun that is also a word of a client's name and is read as that client (the page's line shows it); a turn whose client list cannot be read (the store failed), where nothing is mapped and the question goes as typed, as before this ticket; and a name inside a client's message in a thread result (T11.6a, which consent (b)'s text names); texts in English and German for any line the page adds; a progress entry.
- [ ] `code-reviewer` and `compliance-reviewer` (what goes into model messages changes: fewer names), their reports on the PR; `/security-review`, as the coach's prompt input changes.

**Needs the owner** (Claude's recommendation first):
1. **Which words are read as a client.** The owner chose (a) on 2026-11-28, as Claude recommended (criteria "The matcher's cases" and "The coach sees what was read"). The options were: (a) the full display name, and also any single word of it that no other client of the coach has in their name, typed with a capital first letter and at least two letters ("Sam" for "Demo gymer Sam", but not "Demo" or "gymer", which every demo client has), and a line under the question, written by the page in code, naming whom each matched word was read as ("Sam: read as your client Demo gymer Sam"), so a wrong match is seen at once; the risk is a client whose name is an everyday word ("Will", "May") at the start of a sentence, or, in German, any noun. (b) The full display name only: no wrong matches, but "Sam" is not read when the name is "Demo gymer Sam" or "Sam Müller", which is the case the live check met. (c) A client picker beside the chat that puts the client's reference into the question: exact, but one more click, and a typed name is still sent as typed.
2. **What the page and the PDF show for the question.** The owner chose on 2026-11-28, as Claude recommended: the question as the coach typed it, with the name, in both (the coach's own text, read by the coach only, as today); otherwise the PDF would show "client-1" where the coach wrote a name.

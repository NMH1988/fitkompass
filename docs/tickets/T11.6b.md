### T11.6b The client's thread in the coach's AI chat, part 2: reply drafts and the "AI draft approved by the coach" flag (M) · status: todo · issue none
**Serves:** Capstone (`docs/BRIEF_CAPSTONE.md`): Case 2 steps 1-3 (report generation for the coach: a reply draft from the thread), E2a, E2b, E3; Sprint 3 (`docs/BRIEF_SPRINT3.md`): none; Sprint 2 (`docs/BRIEF.md`): none.
**Depends on:** T11.6a, O21
**Acceptance criteria** (T11.6's, approved by the owner on 2026-11-23, split by the owner on 2026-11-25; the mechanism of the flag chosen by the owner on 2026-11-25, in the Notes)
- [ ] **Reply drafts read one thread only.** On the Messages page the coach can ask for a reply draft to the open thread. It is a fixed workflow (D26's shape, in-memory checkpoints) with no tools, so no other client's data can reach it: the same guarded read of this thread (the `reply` use on), the coach's optional hint (also through the guards), one model call with structured output, the code's checks, then `interrupt()` for the coach. A draft already shown may still be sent after the `reply` use goes off, as a reply is the coach's own message in a thread that already holds what it answers (unlike T11.14's and T11.15's saves, which check the use again). When the `reply` use is off, no model is called and the page shows the same neutral line as when the thread holds no message to answer, in English and German. The draft is labelled as AI-generated in English and German and is sent only after the coach approves or edits it; a reply sent from an AI draft, edited or not, shows the gymer an "AI draft approved by the coach" label in English and German (AC-41's pattern). The reply is sent through the chat socket like every other message (T11.4b has no second send path through the store, owner's choice); the server sets the flag only from state the page records in code for the acting coach and that thread when the coach approves the draft, never from a frame field or anything else the browser sends (the mechanism in the Notes); the message row keeps it, named in `.claude/rules/security-privacy.md`'s list of stored data, in both exports and deleted with the message; a draft not sent is never stored - graph tests with a fake model (an injection asking for another client's numbers: the draft holds none of that client's canary values), store tests, a socket test that a frame cannot set the flag, AppTest.
- [ ] **The `reply` use of consent (b).** T11.6a's switches get the `reply` use, its text (reply drafts: what is sent, the coach's hint included) in English and German with a version of its own, so the `chat` use stays as it is and `reply` starts off; the gymer switches it in one click beside `chat` - store tests, AppTest.
- [ ] **Every message passes the guards first, and the coach sees what was left out.** As in T11.6a, each message and the coach's hint run through the input guard and the domain guardrails first; a rejected message is left out, and the page shows the count and a line asking the coach to read them in the thread under the draft, in code, in English and German - tests, AppTest.
- [ ] Every Sprint 3 guardrail holds for a draft: a reply draft's text passes the domain guardrails' checks (`src/guardrails.py`: no diagnosis, no medical advice, no program), and a kcal number in it below the calorie floor (`CALORIE_FLOOR_KCAL`) is refused in code, as T9.16's and T10.2's checks refuse it in a review - tests reusing those checks.
- [ ] No log line or trace holds a message or a draft: a new case in `tests/test_tracing.py` covers a reply draft run; canary tests in `tests/test_observability.py`.
- [ ] `docs/PRD.md` AC-50 holds whole; `code-reviewer`, `/security-review`, `compliance-reviewer`, and their reports on the PR.

**Notes:** split from T11.6 by the owner on 2026-11-25; its issue is created when the owner agrees (T11.6's issue NMH1988/fitkompass#13 went with T11.6a). **The flag's mechanism (the owner's choice, 2026-11-25, as Claude recommended):** when the coach approves (or edits and approves) a draft, the page records in the process's memory, which the chat socket shares under `streamlit run serve.py`, a mark for the acting coach and that thread with the SHA-256 of the approved text and an expiry of about two minutes; the page hands the approved text to the browser component, which sends it as an ordinary `send` frame; the server sets the flag only when a send from that coach in that thread has exactly that text, and removes the mark, so it labels one message once; discarding the draft or leaving the thread removes the mark too, and nothing about a draft is stored. A message the coach typed alone, sent before the approved one or from a second tab, has another text and gets no label. **From T11.6a's security round 1 (2026-11-25):** the reply-draft run gets only that client's thread and none of the client tools; a draft's text has its links broken, as T11.6a's chat answers have (`recipes.unlinked_markdown()`), and other clients' references and names are checked in code before the coach sees it, as a draft is sent to the gymer.

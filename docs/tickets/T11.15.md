### T11.15 (P2) A suggested foods draft from the client's messages (M) · status: todo · issue NMH1988/fitkompass#30
**Serves:** Capstone (`docs/BRIEF_CAPSTONE.md`): Case 2 steps 1-3 (a workflow that turns the thread into a list the coach approves, with the USDA data as a tool), E2b, E3; Sprint 3 (`docs/BRIEF_SPRINT3.md`): none; Sprint 2 (`docs/BRIEF.md`): none.
**Depends on:** T11.6, O25
**Acceptance criteria** (proposed by Claude at the owner's request and approved by the owner on 2026-11-23, then changed after code review round 1 and compliance run 1 of NMH1988/fitkompass#33 with the owner's choices of the same day, in the Notes)
- [ ] **A draft on the coach's button only.** On the suggested foods editor of Client week (T9.34), shown while the client shares nutrition (as `suggestions.add_client_suggestions()` requires), the coach presses a button to draft a list from the client's messages. Right before the model call the graph checks again the relationship, the nutrition share and that the client's consent (b) for this coach has its `foods` use on (T11.6's switches); without the use, no model is called and the coach sees the same neutral line as when the client sent no message that week, so the page never states which choice the client made - AppTest of both cases with the same text, graph tests with a fake model that is never called.
- [ ] **The model proposes, the code decides.** The graph reads the client's own messages of the current week through T11.6's guarded read (a rejected one left out and counted) and the client's current target, and asks the model with structured output for foods by name, each with a meal slot and grams; code matches every name to the local USDA table (`data/usda_foods.csv`, never the FoodData Central API), drops a name with no match, refuses grams outside `config.FOOD_MIN_GRAMS` to `config.FOOD_MAX_GRAMS`, keeps at most `config.MAX_SUGGESTED_FOODS` and a food at most once per slot, and passes each name through the domain guardrails' checks (no medical diet) - graph tests with scripted proposals (unknown food, grams out of range, duplicates, a medical claim).
- [ ] **The coach approves.** The draft is shown to the coach labelled as AI-generated in English and German, with the count of messages left out; the coach edits, approves or discards it; only an approved list is saved, through `suggestions.add_client_suggestions()` (its access check and its `suggestions_set` audit row), and only after the save checks again the relationship and the `foods` use (and, when the draft used client notes, consent (e), T11.16); when one fails nothing is saved, and the Question phase decides what the coach sees (no line that states the client's choice, compliance run 1's finding 4); nothing is saved on discard or when the session ends - store tests, graph tests (the use switched off between the draft and the approval saves nothing), AppTest.
- [ ] **The gymer sees where it came from.** A list saved from an AI draft, edited or not, shows the gymer an "AI draft approved by the coach" label in English and German (AC-41's pattern); the list keeps that flag, named in `.claude/rules/security-privacy.md`'s list of stored data, in both exports and deleted with the list - store tests (a migration that keeps every row), AppTest.
- [ ] **Consent (b)'s text** adds this use with its switch (and says a list saved from a draft stays after the use is switched off), so its version changes, and the gymer is asked only about this use before its first flow, the switches already set staying as they are (`docs/tickets/T11.6.md`, consent (b)'s switches); the editor says, in English and German, that the app checks no allergen or intolerance in a draft, as for recipes - AppTest.
- [ ] No log line or trace holds a message, a food name from the draft or the target (canary tests, a case in `tests/test_tracing.py`).
- [ ] `docs/PRD.md` AC-56 holds; `code-reviewer`, `/security-review`, `compliance-reviewer`, and their reports on the PR.

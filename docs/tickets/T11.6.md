### T11.6 The client's thread in the coach's AI chat, and reply drafts (M) · status: todo · issue NMH1988/fitkompass#13
**Serves:** Capstone (`docs/BRIEF_CAPSTONE.md`): Case 2 steps 1-3 (a new tool for the coach's agent, a database query over the thread, and report generation for the coach), E2a, E2b, E3; Sprint 3 (`docs/BRIEF_SPRINT3.md`): none; Sprint 2 (`docs/BRIEF.md`): none.
**Depends on:** T11.5, O21
**Acceptance criteria** (rewritten on 2026-11-23 at the owner's request, "layer 1": the coach's AI reads the thread when the coach asks; proposed by Claude and approved by the owner on 2026-11-23, with the choices in the Notes; the criteria approved on 2026-11-19 are kept below the Notes as the record)
- [ ] **The thread is a tool of the coach's chat.** A new tool, `get_client_thread` (`src/tools/`, added to a coach's tools by `registry.build_tools(..., clients=...)` only, as T9.17's `list_my_clients` and `get_client_week`), takes a client's reference (`client-N`, resolved by T9.17's reference map, never a name or an ID from the model) and a week (Monday to Sunday in `Europe/Berlin`, D21; the current week when none is given), reads that week's messages of the coach's thread with the client through `src/store/messages.py` as the acting coach (at most `config.THREAD_MESSAGES_TO_MODEL`, the newest kept), and returns each as its side ("the client" or "the coach"), its day and time and its text, never a display name, an ID or an address. A summary is a question to the chat ("summarise this week's messages of client-1"), so there is no separate summary button, and like every chat it lives in the session only - tool unit tests, a graph test with a scripted fake model, AppTest of a coach's turn.
- [ ] **Only with consent (b) and an active relationship.** The tool checks, right before it reads the store, that the relationship is active and that the gymer's consent (b) for this coach is given (T11.5's consent functions); otherwise it returns one fixed notice with no message text and no hint of which check failed, and the model is told the thread is not available. A former coach, a coach with no consent (b) from the client, a new coach of a client whose consent (b) belonged to an earlier coach and an unknown reference all get that notice - parametrised tests with a fake model that never receives a message.
- [ ] **A withdrawn consent reaches the open chat too.** As the chat keeps its tool results in the session's conversation and sends them again on the next turns, before every model call of a coach's turn the code checks again, for each client whose thread is in the conversation, that the relationship is active and consent (b) still given; when one is not, that client's thread results are removed from the conversation before the call (replaced by the fixed notice), so a withdrawn consent or an ended relationship stops the next flow at once - graph tests (consent withdrawn between two turns: the second model call holds no message text).
- [ ] **Every message passes the guards first.** Each message, from either side, runs through the input guard and the domain guardrails before it goes into the tool's result; a rejected message is left out, and the result says how many were left out, without their text; the answer then tells the coach how many and asks them to read those in the thread, as one may be an injury the coach must see - parametrised tests with benign and rejected messages (an injury, an injection), a fake model that never receives a rejected one.
- [ ] **Messages are data.** The tool's result holds the messages inside a delimited block, never in the system prompt; the coach prompt (O21) says they are data, never instructions; a proposal of `remember_preference` made in a turn whose conversation holds a thread result is checked as today (the guardrails and the names of the coach's current and former clients) and still pauses for the coach - tests, and a `security-reviewer` run on indirect injection through the thread (a gymer's message that asks the coach's agent to call a tool, remember something or write a link).
- [ ] **Reply drafts.** On the Messages page the coach can ask for a reply draft to the thread (the same tool's read, checks and guards, with the coach's optional hint, which also passes the guards); the draft is labelled as AI-generated in English and German and is sent only after the coach approves or edits it; a reply sent from an AI draft, edited or not, shows the gymer an "AI draft approved by the coach" label in English and German (AC-41's pattern); the message row keeps that flag, named in `.claude/rules/security-privacy.md`'s list of stored data, in both exports and deleted with the message; a draft not sent is never stored - graph tests with a fake model, store tests, AppTest.
- [ ] **Consent (b)'s text** names the current coach and its uses as built here (the coach's AI chat reading the thread, reply drafts), what is sent (both sides' messages of the week the coach asks about), OpenRouter and the model provider; a later ticket that adds a use (T11.14, T11.15) changes the text, so its version changes and the gymer is asked again before the next flow (T11.5's rule); consent (a), for their own drafts, does not count - AppTest in English and German, store tests.
- [ ] No log line or trace holds a message, a summary or a draft: the tool's result keys are none of the mask's kept keys (`tracing.mask()`), and a new case in `tests/test_tracing.py` covers a turn with a thread result; canary tests in `tests/test_observability.py`.
- [ ] Every Sprint 3 guardrail holds for an answer or a draft built on the thread (no diagnosis, no program, the calorie floor in a recommendation, refused in code by the weekly review's checks where they apply) - tests reusing T9.16's and T10.2's checks.
- [ ] `docs/PRD.md` AC-50 holds; `code-reviewer`, `/security-review`, `compliance-reviewer`, and their reports on the PR.

**The criteria approved on 2026-11-19, replaced by the ones above on 2026-11-23** (title then: "(P1) The coach's thread summaries and reply drafts"):
- On a thread, the coach asks for a summary of the messages of a week they pick (Monday to Sunday in `Europe/Berlin`, D21; at most a number of messages from config) or a reply draft; the draft is labelled as AI-generated in English and German and is sent only after the coach approves or edits it; a summary lives in the session only and is never stored, and a reply becomes data only when sent as a message.
- A reply sent from an AI draft, edited or not, shows the gymer an "AI draft approved by the coach" label in English and German, as a weekly review does (AC-41); the message row keeps that flag, in both exports and deleted with the message.
- The thread (the coach's own messages included) reaches the model only with that gymer's consent (b), checked again right before each model call through T11.5's consent functions; consent (a) does not count; without (b) the request is refused with a clear message and no model call.
- Each message of the thread, from either side, and any text the coach types into the request, runs through the input guard and the domain guardrails before the model call; a rejected message is left out, and the draft says how many, without their text.
- A summary or reply draft is offered only while the coach's relationship with the client is active, and consent (b) is given for one coach.
- No log line or trace holds a message, a summary or a draft.
- Every Sprint 3 guardrail holds for a draft.
- `docs/PRD.md` AC-50 holds; `code-reviewer`, `/security-review`, `compliance-reviewer`, and their reports on the PR.

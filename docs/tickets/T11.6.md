### T11.6 The client's thread in the coach's AI chat, and reply drafts (M) · status: todo · issue NMH1988/fitkompass#13
**Serves:** Capstone (`docs/BRIEF_CAPSTONE.md`): Case 2 steps 1-3 (a new tool for the coach's agent, a database query over the thread, and report generation for the coach), E2a, E2b, E3; Sprint 3 (`docs/BRIEF_SPRINT3.md`): none; Sprint 2 (`docs/BRIEF.md`): none.
**Depends on:** T11.5, O21
**Acceptance criteria** (rewritten on 2026-11-23 at the owner's request, "layer 1": the coach's AI reads the thread when the coach asks; proposed by Claude and approved by the owner on 2026-11-23, then changed after code review round 1 and compliance run 1 of NMH1988/fitkompass#33 with the owner's choices of the same day, in the Notes; the criteria approved on 2026-11-19 are kept below the Notes as the record)
- [ ] **The thread is a tool of the coach's chat.** A new tool, `get_client_thread` (`src/tools/`, added to a coach's tools by `registry.build_tools(..., clients=...)` only, as T9.17's `list_my_clients` and `get_client_week`), takes a client's reference (`client-N`, resolved by T9.17's reference map, never a name or an ID from the model) and a week (Monday to Sunday in `Europe/Berlin`, D21; the current week when none is given), reads that week's messages of the coach's thread with the client through `src/store/messages.py` as the acting coach (at most `config.THREAD_MESSAGES_TO_MODEL`, the newest kept), and returns each as its side ("the client" or "the coach"), its day and time and its text, never a display name, an ID or an address. A summary is a question to the chat ("summarise this week's messages of client-1"), so there is no separate summary button, and like every chat it lives in the session only - tool unit tests, a graph test with a scripted fake model, AppTest of a coach's turn.
- [ ] **Consent (b), one use at a time.** Consent (b) is one row per gymer and relationship with the version of its text, and a switch per use (`chat`: the coach's AI chat reading the thread; `reply`: reply drafts; later `review`, T11.14, and `foods`, T11.15), each turned on or off by the gymer in one click; declining or withdrawing one use leaves the others as they are; the switches are in the gymer's export and go with their data. When a later ticket adds a use and so a new version of (b)'s text, the switches already set stay as they are, the new use starts off, and the gymer is asked only about the new use before its first flow (T11.5's "a changed text asks again" applies to that use alone); the row records the version each switch was set under. If T11.5's table holds no per-use choice, this ticket adds it with a migration of its own (`STRICT`, every row kept) - store tests (each use alone on, alone off; a new version keeps the `chat` use working and starts the new use off; an upgrade keeps every row), AppTest.
- [ ] **Only with that use switched on and an active relationship.** The tool checks, right before it reads the store, that the relationship is active and that the gymer's consent (b) for this coach has its `chat` use on (T11.5's consent functions); otherwise it returns one fixed notice with no message text and no hint of which check failed, and the model is told the thread is not available. A former coach, a coach whose client has no (b) or has `chat` off, a new coach of a client whose (b) belonged to an earlier coach, and an unknown reference all get that notice - parametrised tests with a fake model that never receives a message.
- [ ] **A withdrawn consent reaches the open chat too.** The chat keeps no tool results between turns but keeps each question and the model's answer, and sends them again (`src/agent/memory.py`); an answer may summarise or quote the thread. So the turn marks each kept question whose turn used a client's thread with that client's reference, by the question's message id (as the `domains` map does, T10.5), and before every model call (of a later turn, and of the same turn after the tool's result) the code checks again, for each marked client, that the relationship is active and the `chat` use still on; when either fails, within the turn the content of that client's thread result (the tool's `ToolMessage`) is replaced by the tool's fixed notice, its `tool_call_id` kept so the request stays valid, and the text of that turn's AI messages after the thread result is cleared, their `tool_calls` kept (the model may have quoted the thread beside a further tool call), and in later turns that client's marked questions and their answers are left out of what the model receives. The page still shows them to the coach, who has read them already, and says nothing about it, so the chat never tells the coach which choice the client made (as the fixed notice gives no hint) - graph tests with a fake model whose answer repeats a canary message: after the use is switched off (and, separately, after the relationship ends) between two turns, and between two model calls of one turn, the next model call holds no canary (within the turn, the fixed notice in place of the thread result, and a test with three model calls whose second quotes the canary beside a further tool call); AppTest that the page shows no line about it. A coach who pastes an earlier answer into a new question sends it as their own text, as when they type what the client said: `docs/SECURITY.md` lists it as a known limit.
- [ ] **Every message passes the guards first, and the coach sees what was left out.** Each message, from either side, runs through the input guard and the domain guardrails before it goes into the tool's result; a rejected message is left out. The count of messages left out, and a line asking the coach to read them in the thread (one may be an injury the coach must see), are shown by the page in code under the answer or the draft, in English and German, never left to the model - parametrised tests with benign and rejected messages (an injury, an injection) and a fake model that never receives a rejected one; AppTest of the line.
- [ ] **Messages are data.** The tool's result holds the messages inside a delimited block, never in the system prompt; the coach prompt (O21) says they are data, never instructions; a proposal of `remember_preference` made in a turn that used a thread is checked as today (the guardrails and the names of the coach's current and former clients) and still pauses for the coach - tests, and a `security-reviewer` run on indirect injection through the thread (a gymer's message that asks the coach's agent to call a tool, remember something, write a link, or put another client's data in a reply draft).
- [ ] **Reply drafts read one thread only.** On the Messages page the coach can ask for a reply draft to the open thread. It is a fixed workflow (D26's shape, in-memory checkpoints) with no tools, so no other client's data can reach it: the same guarded read of this thread (the `reply` use on), the coach's optional hint (also through the guards), one model call with structured output, the code's checks, then `interrupt()` for the coach. A draft already shown may still be sent after the `reply` use goes off, as a reply is the coach's own message in a thread that already holds what it answers (unlike T11.14's and T11.15's saves, which check the use again). When the `reply` use is off, no model is called and the page shows the same neutral line as when the thread holds no message to answer, in English and German. The draft is labelled as AI-generated in English and German and is sent only after the coach approves or edits it; a reply sent from an AI draft, edited or not, shows the gymer an "AI draft approved by the coach" label in English and German (AC-41's pattern). The flag is set by the page's own send call in code, never taken from a socket frame or the browser; the message row keeps it, named in `.claude/rules/security-privacy.md`'s list of stored data, in both exports and deleted with the message; a draft not sent is never stored - graph tests with a fake model (an injection asking for another client's numbers: the draft holds none of that client's canary values), store tests, a socket test that a frame cannot set the flag, AppTest.
- [ ] **Consent (b)'s text** names the current coach and the uses built here, each with its switch (the coach's AI chat reading the thread; reply drafts), what is sent (both sides' messages of the week the coach asks about), OpenRouter and the model provider, and says that switching a use off changes nothing else in the coaching; a later ticket that adds a use (T11.14, T11.15) changes the text, so its version changes, and the gymer is asked only about the new use before its first flow (the switches criterion above); consent (a), for their own drafts, does not count - AppTest in English and German (the text names the current coach), store tests.
- [ ] `.claude/rules/security-privacy.md` and `docs/SECURITY.md` name the AI's read of a thread for the coach among the reads that write no audit row (owner's choice, 2026-11-23), beside a person's read of their own thread - review. No log line or trace holds a message, a summary or a draft: the tool's result keys are none of the mask's kept keys (`tracing.mask()`), and a new case in `tests/test_tracing.py` covers a turn with a thread result and a reply draft run; canary tests in `tests/test_observability.py`.
- [ ] Every Sprint 3 guardrail holds for an answer or a draft built on the thread: a reply draft's text passes the domain guardrails' checks (`src/guardrails.py`: no diagnosis, no medical advice, no program), and a kcal number in it below the calorie floor (`CALORIE_FLOOR_KCAL`) is refused in code, as T9.16's and T10.2's checks refuse it in a review - tests reusing those checks.
- [ ] `docs/PRD.md` AC-50 holds; `code-reviewer`, `/security-review`, `compliance-reviewer`, and their reports on the PR.

**The criteria approved on 2026-11-19, replaced by the ones above on 2026-11-23** (title then: "(P1) The coach's thread summaries and reply drafts"):
- On a thread, the coach asks for a summary of the messages of a week they pick (Monday to Sunday in `Europe/Berlin`, D21; at most a number of messages from config) or a reply draft; the draft is labelled as AI-generated in English and German and is sent only after the coach approves or edits it; a summary lives in the session only and is never stored, and a reply becomes data only when sent as a message.
- A reply sent from an AI draft, edited or not, shows the gymer an "AI draft approved by the coach" label in English and German, as a weekly review does (AC-41); the message row keeps that flag, in both exports and deleted with the message.
- The thread (the coach's own messages included) reaches the model only with that gymer's consent (b), checked again right before each model call through T11.5's consent functions; consent (a) does not count; without (b) the request is refused with a clear message and no model call.
- Each message of the thread, from either side, and any text the coach types into the request, runs through the input guard and the domain guardrails before the model call; a rejected message is left out, and the draft says how many, without their text.
- A summary or reply draft is offered only while the coach's relationship with the client is active, and consent (b) is given for one coach.
- No log line or trace holds a message, a summary or a draft.
- Every Sprint 3 guardrail holds for a draft.
- `docs/PRD.md` AC-50 holds; `code-reviewer`, `/security-review`, `compliance-reviewer`, and their reports on the PR.

### T11.3 Coach-client messages in the store (M) · status: todo · issue NMH1988/fitkompass#9
**Serves:** Capstone (`docs/BRIEF_CAPSTONE.md`): Case 2 step 2 (the database the agent's tools read), Case 2 step 4 in part, E3; Sprint 3 (`docs/BRIEF_SPRINT3.md`): none; Sprint 2 (`docs/BRIEF.md`): none.
**Depends on:** T11.2 (order only)
**Acceptance criteria** (proposed by Claude and approved by the owner, 2026-11-19, with the choices in the Notes)
- [ ] A migration adds a `messages` table (thread = the coach-client relationship, sender, time, text with a length limit from config); a message is written only by a side of an active relationship; a thread is read only by its two sides, checked by the relationship (like `users.display_name_of()`), not by a sharing scope, and also after the relationship ends, read-only; every other case gets the same `NotFound` and writes no row - the new functions in a group of their own in `tests/test_store_access.py` (a stranger, a former coach of another client, a write after the end refused; a read after the end allowed). A thread read is not audited, as both readers are parties to the conversation and an audit row for every pushed message would flood the log: an exception to "every coach read is audited", recorded in `.claude/rules/security-privacy.md` with the owner's choice, as T9.12's and T9.30's are.
- [ ] Messages are in both sides' export and are deleted with either side's data - `tests/test_store_my_data.py` (or its equivalent) with the new table named in `my_data.delete_user_data()` and `export_user_data()`.
- [ ] A new message is a notification kind (D23), worked out from the rows, holding no text, seen only by the other side - notification tests.
- [ ] No log line or trace holds a message's text - a canary test in `tests/test_observability.py`.
- [ ] The store's connection settings let a second process (T11.4's server) read and write the same file safely (WAL and a busy timeout, or what the Research phase finds) - a test with two connections.
- [ ] What the app tells the users matches the thread's rules: the text shown when a relationship ends (`sharing.end_note`, `src/i18n/account.py`) says the former coach still reads the thread, read-only, and no other record; the gymer's My data intro (`my_data.intro_gymer`) says thread reads are not audited, so they are not in the export; `docs/PRD.md`'s "Who sees what" names the thread - AppTest in English and German, review.
- [ ] `.claude/rules/security-privacy.md` ("Personal data", "The store") and `docs/SECURITY.md` name the messages; `docs/PRD.md` AC-45's store part holds - review; `code-reviewer`, `compliance-reviewer` (new stored personal data), and their reports on the PR.
**Notes:** **the owner's choices (2026-11-19):** the read is relationship-based, no new scope (messages are correspondence between the two, not data the gymer shares); thread reads are not audited (recorded exception); after the relationship ends both sides keep read-only access and nobody can send, and the thread goes when either side deletes their data. No UI yet (T11.4b shows the thread). Every query a module constant with `?` parameters (`tests/test_store_sql_scan.py`). Messages are never sent to a model in this ticket. From the reviews of PR NMH1988/fitkompass#22 (2026-11-19): WAL mode adds `-wal` and `-shm` files next to the store file, so the Question phase checks `.gitignore`, the delete path (`docs/SECURITY.md`'s note on deleted rows) and how an existing store file is moved to WAL. The owner approved this criterion, added after compliance run 1 of NMH1988/fitkompass#22, on 2026-11-19. For the Question phase: both My data intros (the gymer's and the coach's) list the messages among what is stored and exported.

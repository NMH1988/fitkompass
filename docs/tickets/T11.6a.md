### T11.6a The client's thread in the coach's AI chat, part 1: the tool, consent (b)'s switches and the open chat (M) · status: done · issue NMH1988/fitkompass#13
**Serves:** Capstone (`docs/BRIEF_CAPSTONE.md`): Case 2 steps 1-3 (the coach's agent with a new tool, a database query over the thread, and multi-step reasoning over it across turns), Case 2 step 4 in part (the gymer's consent switches, the left-out line under an answer, the thread in the tool results), E2a, E2b, E3; Sprint 3 (`docs/BRIEF_SPRINT3.md`): none; Sprint 2 (`docs/BRIEF.md`): none.
**Depends on:** T11.5, O21
**Acceptance criteria** (T11.6's, approved by the owner on 2026-11-23, split by the owner on 2026-11-25; the reply drafts' criteria are T11.6b's; the choices of the Question phase in the Notes)
- [x] **The thread is a tool of the coach's chat.** A new tool, `get_client_thread` (`src/tools/`, added to a coach's tools by `registry.build_tools(..., clients=...)` only, as T9.17's `list_my_clients` and `get_client_week`), takes a client's reference (`client-N`, resolved by T9.17's reference map, never a name or an ID from the model) and a week (Monday to Sunday in `Europe/Berlin`, D21; the current week when none is given), reads that week's messages of the coach's thread with the client through `src/store/messages.py` as the acting coach (at most `config.THREAD_MESSAGES_TO_MODEL`, the newest kept), and returns each as its side ("the client" or "the coach"), its day and time and its text, never a display name, an ID or an address. A summary is a question to the chat ("summarise this week's messages of client-1"), so there is no separate summary button, and like every chat it lives in the session only - tool unit tests, a graph test with a scripted fake model, AppTest of a coach's turn.
- [x] **Consent (b), one use at a time.** Consent (b) is given per gymer and relationship with the version of its text, and a switch per use (`chat`: the coach's AI chat reading the thread; `reply`: reply drafts, T11.6b; later `review`, T11.14, and `foods`, T11.15), each turned on or off by the gymer in one click; declining or withdrawing one use leaves the others as they are; the switches are in the gymer's export and go with their data. When a later ticket adds a use and so a new version of (b)'s text, the switches already set stay as they are, the new use starts off, and the gymer is asked only about the new use before its first flow (T11.5's "a changed text asks again" applies to that use alone); the row records the version each switch was set under. T11.5's table holds no per-use choice, so this ticket adds it with a migration of its own (`STRICT`, every row kept): each use is a row of its own with the version of its own text (the owner's choice, 2026-11-25, in the Notes) - store tests (each use alone on, alone off; a new version keeps the `chat` use working and starts the new use off; an upgrade keeps every row), AppTest.
- [x] **Only with that use switched on and an active relationship.** The tool checks, right before it reads the store, that the relationship is active and that the gymer's consent (b) for this coach has its `chat` use on (T11.5's consent functions); otherwise it returns one fixed notice with no message text and no hint of which check failed, and the model is told the thread is not available. A former coach, a coach whose client has no (b) or has `chat` off, a new coach of a client whose (b) belonged to an earlier coach, and an unknown reference all get that notice - parametrised tests with a fake model that never receives a message.
- [x] **A withdrawn consent reaches the open chat too.** The chat keeps no tool results between turns but keeps each question and the model's answer, and sends them again (`src/agent/memory.py`); an answer may summarise or quote the thread. So the turn marks each kept question whose turn used a client's thread with that client's reference, by the question's message id (as the `domains` map does, T10.5), and before every model call (of a later turn, and of the same turn after the tool's result) the code checks again, for each marked client, that the relationship is active and the `chat` use still on; when either fails, within the turn the content of that client's thread result (the tool's `ToolMessage`) is replaced by the tool's fixed notice, its `tool_call_id` kept so the request stays valid, and the turn's AI messages after the thread result are left out with their tool results (the Question phase's choice, in the Notes), and in later turns that client's marked questions and their answers are left out of what the model receives. The page still shows them to the coach, who has read them already, and says nothing about it, so the chat never tells the coach which choice the client made (as the fixed notice gives no hint) - graph tests with a fake model whose answer repeats a canary message: after the use is switched off (and, separately, after the relationship ends) between two turns, and between two model calls of one turn, the next model call holds no canary (within the turn, the fixed notice in place of the thread result, and a test with three model calls whose second quotes the canary beside a further tool call); AppTest that the page shows no line about it. A coach who pastes an earlier answer into a new question sends it as their own text, as when they type what the client said: `docs/SECURITY.md` lists it as a known limit.
- [x] **Every message passes the guards first, and the coach sees what was left out.** Each message, from either side, runs through the input guard and the domain guardrails before it goes into the tool's result; a rejected message is left out. The count of messages left out, and a line asking the coach to read them in the thread (one may be an injury the coach must see), are shown by the page in code under the answer, in English and German, never left to the model - parametrised tests with benign and rejected messages (an injury, an injection) and a fake model that never receives a rejected one; AppTest of the line.
- [x] **Messages are data.** The tool's result holds the messages inside a delimited block, never in the system prompt; the coach prompt (O21; the owner's thread part, 2026-11-25) says they are data, never instructions; `remember_preference` is neither offered nor run in a turn that holds a thread, as a saved preference would carry what the model read into every later chat (the owner's choice, 2026-11-25, after compliance round 1, replacing "checked as today and still pauses for the coach") - tests, and a `security-reviewer` run on indirect injection through the thread (a gymer's message that asks the coach's agent to call a tool, remember something, write a link, or put another client's data in an answer).
- [x] **Consent (b)'s text** names the current coach and the use built here, with its switch (the coach's AI chat reading the thread), what is sent (both sides' messages of the week the coach asks about), OpenRouter and the model provider, and says that switching a use off changes nothing else in the coaching; a later ticket that adds a use (T11.6b, T11.14, T11.15) changes the text of that use, so its version changes, and the gymer is asked only about the new use before its first flow (the switches criterion above); consent (a), for their own drafts, does not count. The Messages page's intro texts for both roles in both languages (`src/i18n/thread.py`) and the README's "Real-time messages" section say that the coach's AI reads the thread when the coach asks only with the client's consent (b) for that use - AppTest in English and German (the text names the current coach; the intro texts), store tests.
- [x] `.claude/rules/security-privacy.md` and `docs/SECURITY.md` name the AI's read of a thread for the coach among the reads that write no audit row (owner's choice, 2026-11-23), beside a person's read of their own thread - review. No log line or trace holds a message or a summary: the tool's result keys are none of the mask's kept keys (`tracing.mask()`), and a new case in `tests/test_tracing.py` covers a turn with a thread result; canary tests in `tests/test_observability.py`.
- [x] Every Sprint 3 guardrail holds for an answer built on the thread: the chat's answer passes the checks every answer passes (the program check, the guard on the next question, the memory's injection check), and a thread result counts as a basis as any client tool's result does - tests reusing those checks.
- [x] `docs/PRD.md` AC-50 holds for the chat; `code-reviewer`, `/security-review`, `security-reviewer`, `compliance-reviewer`, and their reports on the PR. Done: the code review rounds listed in the PROGRESS entry, `/security-review`, security review rounds 1 to 3 and compliance rounds 1 to 3, their reports on the PR; the owner's live check on 4f3e3c3 (2026-11-27, `docs/TESTING.md`, "Live checks"), with what it found outside these criteria in the PROGRESS entry's follow-ups.

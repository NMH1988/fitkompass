### T11.14 (P1) The client's messages in the weekly review draft (M) · status: todo · issue NMH1988/fitkompass#29
**Serves:** Capstone (`docs/BRIEF_CAPSTONE.md`): Case 2 steps 1-3 (the weekly review workflow gains a database query and multi-step reasoning over the thread), E2b, E3; Sprint 3 (`docs/BRIEF_SPRINT3.md`): none; Sprint 2 (`docs/BRIEF.md`): none.
**Depends on:** T11.6, O25
**Acceptance criteria** (proposed by Claude at the owner's request and approved by the owner on 2026-11-23, then changed after code review round 1 and compliance run 1 of NMH1988/fitkompass#33 with the owner's choices of the same day, in the Notes)
- [ ] **The review reads the client's messages of its week, checked at each draft.** When a coach starts a weekly review (T9.16, D17) and the client's consent (b) for this coach has its `review` use on (T11.6's switches), each draft step (the first draft and a second one after failed checks) checks again the relationship and that use right before its model call, then gets the client's own messages of the review's week (Monday to Sunday in `Europe/Berlin`, at most `config.THREAD_MESSAGES_TO_MODEL`, never the coach's messages), each through the input guard and the domain guardrails first, a rejected one left out and its count shown to the coach in code. Without the use, the review runs as today with no message - graph tests with a scripted fake model (with and without the use, the use switched off between the first and the second draft, a rejected message never reaching the model).
- [ ] **One neutral line.** The coach sees the same line, in English and German, when no message was used because the use is off and when the client sent no message that week ("No client messages were used for this draft"), so the review never states which choice the client made (the coach may still guess it from the thread) - AppTest of both cases with the same text.
- [ ] **Message text in the review's checkpoints only as approved statements.** The messages are read from the store inside the draft step and passed to the model there; `ReviewState`, checkpointed in the SqliteSaver file (D12), keeps only the IDs of the messages used and the count left out, never their text. The draft itself (`ReviewState.draft`) is checkpointed too and may word or quote a message in a "client reported" statement, so `.claude/rules/security-privacy.md` and `docs/SECURITY.md` change their line on that file ("metrics, not chat messages") to say so - a test with a fake model that quotes one message: the checkpointer file holds no canary of a message it did not quote, and none at all outside the draft.
- [ ] **What the review says from a message is marked and checked.** A statement taken from the client's messages is a statement of its own kind ("the client reported", e.g. poor sleep or a busy week), which cites the IDs of the messages it comes from; code refuses a draft whose statement of that kind cites a message that was not passed to it, or that states a number the cited messages do not hold; a recommendation still needs the metrics or a cited source as today, never a message alone; the coach and, once approved, the gymer see such a statement labelled "from the client's messages" in English and German - `src/weekly_review.py` validation tests, AppTest.
- [ ] **Consent (b)'s text** adds this use with its switch (the client's own messages of the week in their coach's weekly review drafts, kept in the approved review the client reads), says that such statements stay in an approved review after the use is switched off or (b) is withdrawn, and in a draft already made that the coach may still approve, and that the gymer can delete them, so its version changes and the gymer is asked again before the next flow (T11.5's rule) - AppTest in English and German; a store test of the gymer's delete (the statement or the review, as the Question phase decides).
- [ ] The approved review keeps such statements as it keeps the others (the reviews table, in both exports, deleted with the review's data), and `docs/PRD.md`'s "Newly stored" names them; the field descriptions the model reads for the new kind are approved by the owner (O25) - store tests, review.
- [ ] No log line or trace holds a message or a statement drawn from one (canary tests in `tests/test_observability.py`, a case in `tests/test_tracing.py`); every Sprint 3 guardrail of the review still holds (T9.16's and T10.2's checks).
- [ ] `docs/PRD.md` AC-55 holds; `code-reviewer`, `/security-review`, `compliance-reviewer`, and their reports on the PR.

**Notes:** the owner's idea of 2026-11-23 (the AI learns from the coach and gymer's conversation to help with the weekly review); planned as its own ticket after T11.6, which builds the guarded read of the thread and the switches of consent (b) this ticket reuses. **The owner's choices (2026-11-23, as Claude proposed them):** P1; only the client's own messages (the coach's advice is not evidence about the client's week); a review without the use still runs; the "client reported" kind never carries a recommendation alone. **After code review round 1 and compliance run 1 of NMH1988/fitkompass#33 (owner's choices, 2026-11-23):** a switch of its own inside (b) (compliance finding 1); the statements stay in approved reviews after withdrawal, said in the text, with the gymer able to delete them (compliance finding 3); the neutral line (compliance finding 4); no audit row for the AI's read of the thread. For the Question phase: whether the "client reported" statements count toward the review's minimum of logged days (proposed: no, they are not logged data); whether the gymer deletes one statement (a new review row without it, as records are never updated in place) or the whole review; how the gymer corrects a statement (GDPR Art. 16, on the PRD's list before any real user).

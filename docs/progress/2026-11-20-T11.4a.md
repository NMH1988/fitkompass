- **Why:** the server comes before the browser component (T11.4b) so it can be tested without a browser, through FastAPI's `TestClient` and a real uvicorn server. A verified token is the server's only source of the acting user (D24), so nothing the browser sends otherwise can name a user or a thread. Pushing through `list_messages(after_id=<the socket's last ID>)` makes the push, the access check and the catch-up one read, so no message is skipped or sent twice. Routing uvicorn's loggers through our formatter is stricter than keeping them at WARNING in their own format: even a warning keeps only its level and logger name.
- **Decisions & gotchas:** the owner's choices in the Question phase (2026-11-20): in demo mode the server takes the store's path (`--store`), so D18's temporary store stays and T11.4b's launcher hands the path to both processes; a notification also goes to the other side's sockets on other threads. Defaults stated then: FastAPI as D24 says; a token of our own with the standard library (no JWT package); port 8510 (Streamlit moves to 8502 when 8501 is taken); a missing `Origin` refused; one close code for every refusal (4401), 1011 for an error; the browser gets `mine`, never a user ID; a `ready` frame after each token's catch-up (a renewal then proves nothing arrived in between, which the tests use). **Found in Research:** FastAPI 0.165 has OpenTelemetry of its own, on when a tracer provider is configured in the process or `FASTAPI_OTEL_AUTO_CONFIGURE` is set, and its logs record an error's message and stack trace; `create_app()` turns all of it off, and a test sets the variable. `db.connect()` with a path creates a missing file, so `main()` checks that the file exists first. A token's expiry is in whole seconds, so with a lifetime of 1 second a token may live less than one; the renewal test uses 2. The module is `tokens.py`, not `token.py`, to keep clear of the standard library's `token`. A mutation check (uvicorn's own logging config at INFO, the routing removed) made the canary test fail on the token in the access log, so the test catches a leak there.

- **Why:** T11.4a's chat server writes and reads the thread from a second process, and T11.5 drafts from it; the store comes first so the server only calls it (D24). The read follows the relationship, not a scope, as messages are correspondence between the two (owner's choices, 2026-11-19). WAL lets one process commit while the other reads (in the old mode a commit waits for every reader, so a long-lived read could make a write fail with "database is locked"); a store that cannot be switched is refused instead.
- **Decisions & gotchas:** the owner's choices in the Question phase (2026-11-20): one notification per thread, not per message; 1000 characters; no fallback from WAL; the whole thread in each side's export. A pair that connects again gets a new thread; the old one stays read-only. The end is read as a value (`ended_at`), never as a status filter, which only `open_shares` may write (`tests/test_store_access.py`'s scan). With WAL a reader no longer blocks a commit, so `test_a_failed_commit_leaves_no_open_transaction` keeps its file in rollback-journal mode to still make COMMIT fail. The deleted rows' bytes test now reads the `-wal` file too, while the store is still open. `tests/test_config_package.py` froze config's names at T10.8's split; it now has `NEW_NAMES` for names added since. **The owner, after merging:** nothing to do by hand; the local store moves to WAL on the app's first run (with the app stopped before pulling, as for any migration).
